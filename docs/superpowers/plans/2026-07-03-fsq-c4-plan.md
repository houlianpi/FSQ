# FSQ2.0 C4 Plan

## 1. 目标

本计划定义 FSQ2.0 在 C4 周期内的交付范围。C4 规划为 6 个 Scrum，每个 Scrum 两周。前 4 个 Scrum 分别完成一个平台适配，S5 用于代码整理和重构，S6 作为 buffer，用于吸收延期项、稳定质量和完成收口。

本计划面向两类读者：

- 不熟悉 FSQ 的业务和管理相关方，需要快速理解 FSQ 是什么、FSQ2.0 解决什么问题。
- FSQ 研发和测试参与者，需要明确 C4 每个 Scrum 的交付物、验收标准和风险边界。

## 2. FSQ 简介

FSQ 是一个面向 AI 测试自动化的系统，核心围绕 FSQ YAML 测试 DSL 和共享执行架构展开。它支持两条互补的工作流：

- 回归执行流：经过评审的 FSQ YAML 可以作为稳定的回归测试用例执行，不需要每次都依赖 Agent 重新理解测试意图。
- 探索生成流：自然语言目标可以经过模型规划、执行、修复和优化，最终沉淀为可复用的 FSQ YAML 测试用例。

FSQ2.0 的关键设计是让这两条流共享同一套执行核心、平台 Harness、证据模型、验证器、报告系统、调试产物和知识系统。这样，AI 生成的测试和人工维护的回归测试不会变成两套割裂系统，而是逐步收敛到统一的动作协议、执行证据和质量判断标准上。

## 3. 为什么要做 FSQ2.0

FSQ2.0 是为了解决 FSQ1.0 在可复现性、平台扩展、证据质量、调试效率和长期维护性上的问题而启动的迭代。

FSQ2.0 的主要特点包括：

- 双循环架构：确定性的 YAML 回归执行和 AI 辅助的探索/用例生成都是一等能力。
- 共享执行核心：YAML 回放、动态规划、步骤执行、重试策略、事件记录、证据采集、验证和报告尽量使用同一条执行路径。
- 平台化 Harness 层：Android、Windows、iOS、macOS 的适配通过平台 Harness 合约组织，避免平台逻辑散落在执行链路中。
- 证据驱动验证：截图、UI Tree、UI Snapshot、工具日志、断言记录和验证器判断会作为调试和质量判断依据保存。
- 可调试失败模型：失败可以通过步骤时间线、截图、UI 层级、工具调用日志、断言证据和验证器判断进行追踪。
- 知识系统：成功用例、页面/界面跳转、稳定定位候选、失败模式和修复经验可以被回归执行和探索生成共同复用。
- 模型/Provider 抽象：Planner 和 Verifier 不绑定单一模型供应方，为后续模型升级或供应方切换保留空间。

## 4. C4 总体目标

C4 结束时，FSQ2.0 需要完成 Android、Windows、iOS、macOS 四个平台的适配验证，并通过足够数量的转换用例和稳定运行数据证明 FSQ2.0 架构可以支撑真实回归测试场景。

平台级验收指标：

- 每个平台至少完成 100 个 testcase 的转换。
- 每个平台稳定运行成功率达到 95% 以上。

这里的“稳定运行成功率”建议定义为：转换后的 testcase 在约定的实验室或 CI 环境中重复运行，排除有明确记录的环境中断、设备不可用、账号/凭证失效、被测应用服务异常等非 FSQ 原因后，成功率达到 95% 以上。

## 5. C4 Scrum 规划

| Scrum | 周期 | 主题 | 核心目标 | 验收标准 |
|---|---:|---|---|---|
| S1 | 2 周 | Android 平台适配 | 完成 Android 平台 C4 目标用例集适配。 | 至少转换 100 个 Android testcase；稳定运行成功率 >= 95%；失败用例具备证据和分类。 |
| S2 | 2 周 | Windows 平台适配 | 完成 Windows 桌面平台适配。 | 至少转换 100 个 Windows testcase；稳定运行成功率 >= 95%；Windows 环境假设和配置要求完成记录。 |
| S3 | 2 周 | iOS 平台适配 | 完成 iOS 平台适配，或完成支持用例转换的最小可用 iOS Harness 路径。 | 至少转换 100 个 iOS testcase；稳定运行成功率 >= 95%；如涉及新平台公共合约，需先完成 SPEC 确认。 |
| S4 | 2 周 | macOS 平台适配 | 完成 macOS 桌面平台适配。 | 至少转换 100 个 macOS testcase；稳定运行成功率 >= 95%；macOS Appium/Mac2 环境假设完成记录。 |
| S5 | 2 周 | 代码整理和重构 | 收敛前 4 个平台适配过程中产生的重复逻辑和临时实现。 | 跨平台动作模式和能力元数据进一步统一；重复适配逻辑减少；已完成平台回归不退化。 |
| S6 | 2 周 | Buffer 和稳定化 | 吸收延期项、修复高优先级问题、完成 C4 收口。 | 阻塞问题关闭或明确记录；最终 C4 指标完成收集；输出 C4 readiness summary。 |

## 6. 分 Scrum 交付说明

### S1: Android 平台适配

S1 用于证明 FSQ2.0 的回归执行流和共享执行核心可以支撑 Android 平台规模化用例执行。

主要交付物：

- 至少 100 个 Android testcase 转换结果。
- 转换用例的运行证据，包括截图、UI Tree、工具日志和断言记录。
- 不稳定用例的失败分类，区分 testcase 问题、Harness 问题、被测应用问题和环境问题。
- 高价值不稳定用例的修复记录。

验收目标：

- Android 转换用例数 >= 100。
- 稳定运行成功率 >= 95%。
- 剩余失败均有证据和责任分类。

### S2: Windows 平台适配

S2 用于验证 FSQ2.0 的平台能力注册、桌面 Harness 和 UI Snapshot 证据模型能否支持 Windows 桌面自动化。

主要交付物：

- 至少 100 个 Windows testcase 转换结果。
- Windows 运行环境说明，包括应用路径、backend 类型、启动参数、窗口标题匹配等环境依赖。
- 基于 Windows UI Snapshot 的证据产物。
- 桌面动作能力在转换用例中的覆盖验证。

验收目标：

- Windows 转换用例数 >= 100。
- 稳定运行成功率 >= 95%。
- 环境假设和配置要求清晰可复现。

### S3: iOS 平台适配

S3 用于完成 iOS 平台适配。由于当前根规格中 iOS 仍属于未来平台方向，S3 如果涉及新的公共平台合约，需要先通过仓库 SDD 流程确认 iOS platform block、能力面、Harness 合约、driver backend 和证据命名，再进入正式实现和验收。

主要交付物：

- 如需要新增公共平台能力，先完成 iOS 相关设计和 SPEC 确认。
- 至少 100 个 iOS testcase 转换结果。
- 可支持转换用例确定性回放的 iOS Harness 路径。
- 与 FSQ2.0 共享执行模型一致的证据采集和失败分类。

验收目标：

- iOS 转换用例数 >= 100。
- 稳定运行成功率 >= 95%。
- 新平台决策在 SPEC 中记录后再作为实现依据。

### S4: macOS 平台适配

S4 用于验证 macOS 桌面自动化路径，重点关注 Appium/Mac2 运行链路、桌面动作能力和 UI Snapshot 证据模型。

主要交付物：

- 至少 100 个 macOS testcase 转换结果。
- macOS 运行环境说明，包括 Appium server URL、bundle id、app path 等环境依赖。
- 基于 macOS UI Snapshot 的证据产物。
- launch、interaction、assertion、screenshot、uiSnapshot 等关键动作流验证。

验收目标：

- macOS 转换用例数 >= 100。
- 稳定运行成功率 >= 95%。
- 环境假设和配置要求清晰可复现。

### S5: 代码整理和重构

S5 用于收敛前四个适配 Scrum 中暴露出的重复逻辑、临时实现和跨平台不一致。目标不是引入新架构，而是在不破坏已完成平台能力的前提下提升可维护性。

主要交付物：

- 减少平台 adapter、Harness 初始化、证据采集、报告链路中的可避免重复。
- 统一命名、能力元数据、错误分类和动作模式中可以共享的部分。
- 保持平台特有逻辑在平台参数模型、动作目录、Harness、driver、config block 和 skill Markdown 中。
- 若实现暴露出 SPEC 缺口，按 SDD 流程更新对应规格。

验收目标：

- 已完成平台 testcase 仍满足成功率目标。
- 相关 `SPEC.md` 与代码行为保持一致。
- 重构不引入平台退化。

### S6: Buffer 和稳定化

S6 用于吸收 S1-S5 延期项、解决高优先级稳定性问题，并准备 C4 收口材料。该 Scrum 应优先处理有证据支撑的稳定性和阻塞问题，不建议再扩大新功能范围。

主要交付物：

- 修复或记录 S1-S5 遗留阻塞问题。
- 重新运行各平台 testcase 集合并收集最终转换数量和成功率。
- 关闭高影响 flaky case，或完成清晰的问题归因。
- 输出 C4 readiness summary，覆盖平台状态、已知风险和下一周期建议。

验收目标：

- 四个平台都有最终 C4 指标。
- 遗留风险具备 owner、影响范围和建议下一步。
- C4 收口报告可用于评审。

## 7. 跨 Scrum 执行规则

- 涉及公共行为、平台合约或架构变化时，必须走仓库 SDD 流程。
- 根 `SPEC.md` 是项目级 source of truth；模块级 `SPEC.md` 负责模块合约。
- testcase 转换应分批完成并持续运行，不要等到 Scrum 末尾集中验证。
- 每个失败或 flaky case 在进入 triage 前都应有证据。
- 不要只看总体成功率，要分别统计 testcase 缺陷、Harness 缺陷、应用缺陷和环境缺陷。
- 优先使用能力元数据和证据策略驱动行为，避免在执行链路中硬编码平台 action name 分支。

## 8. 指标跟踪

每个平台建议持续跟踪：

- 已转换 testcase 数量。
- 可执行 testcase 数量。
- 稳定运行成功率。
- flaky case 数量。
- Top 失败分类。
- 平均失败归因时间。
- 已修复或已稳定 testcase 数量。
- 未关闭平台/Harness 缺陷数量。

建议的 Scrum 汇报表：

| Platform | Converted | Executable | Stable Success Rate | Flaky | Blocking Defects | Notes |
|---|---:|---:|---:|---:|---:|---|
| Android | 100+ | S1 统计 | >= 95% target | S1 统计 | S1 统计 | S1 owner |
| Windows | 100+ | S2 统计 | >= 95% target | S2 统计 | S2 统计 | S2 owner |
| iOS | 100+ | S3 统计 | >= 95% target | S3 统计 | S3 统计 | S3 owner |
| macOS | 100+ | S4 统计 | >= 95% target | S4 统计 | S4 统计 | S4 owner |

## 9. 主要风险

- iOS 可能需要先补齐平台 SPEC 和 Harness 合约，否则实现边界不清晰。
- 平台环境不稳定会影响成功率统计，需要明确排除规则和证据记录。
- testcase 转换可能只做到“能跑一次”，但达不到稳定回归标准。
- S5 重构如果缺少跨平台回归验证，可能引入平台退化。
- S6 buffer 容易被前序延期项消耗，因此每个平台 Scrum 内部也需要预留稳定化时间。

## 10. C4 退出标准

C4 成功的判断标准：

- Android、Windows、iOS、macOS 每个平台至少完成 100 个 testcase 转换。
- 每个平台稳定运行成功率达到 95% 以上。
- 平台失败有证据、有分类、有 owner。
- FSQ2.0 架构收益在实践中可见：共享执行、共享证据、复用验证/报告、平台 Harness 隔离。
- S5 代码整理不导致已完成平台退化。
- C4 readiness summary 可以支撑下一周期规划。
