# FSQ Agent 目录迁移与模块分类指南

本文解释 2026 年 8 月完成的 `fsq_agent` 包目录迁移：为什么迁移、各类代码应该归到哪里、未来何时还需要迁移，以及迁移完成的判定标准。它是团队参考文档，不替代根目录和各模块的 `SPEC.md`；当前模块契约、公共接口和依赖方向始终以相关 `SPEC.md` 为准。

## 一句话结论

这次迁移不是为了让目录看起来更整齐，而是让**业务用例、外部协议、执行编排、平台无关机制和平台实现各有唯一所有者**。长期目标不是持续搬目录，而是让新代码一开始就进入正确边界，使目录迁移成为少数、可论证的架构修正。

## 背景：为什么要迁移

迁移前，代码按早期功能增长自然聚集：CLI、Control Plane、Playground、Agent 和 `core` 中同时包含了协议适配、用例编排、执行策略、平台驱动与环境检查。随着 Web、Android、Windows 和 macOS 能力增加，这种组织方式产生了几个问题：

- 同一个用例在多个入口重复编排，行为容易漂移。
- `core` 同时承担抽象机制与具体平台实现，依赖边界不清晰。
- OpenAI Agents SDK 等外部运行时细节进入 `agent`，策略与供应商适配耦合。
- Case DSL、环境准备、自动化驱动等不同职责仅因历史原因共处。
- 包根目录出现跨入口共享的组合帮助函数，难以确定真正所有者。
- 新同学能看到“文件在哪里”，却难以回答“为什么由这里负责”。

因此，迁移采用分批、行为保持的方式建立职责边界。每一批都保持可发布、可测试，外部 CLI、HTTP/SSE、Case、配置、工作区和证据契约不因目录移动而改变。

## 当前目录如何分类

判断归属时先问“谁拥有规则”，不要先问“哪个入口正在调用它”。

| 分类 | 当前目录 | 放入这里的内容 | 不应放入这里的内容 |
| --- | --- | --- | --- |
| 用例层 | `fsq_agent/application/` | 面向 Case、Run、Provider、Environment、Workspace 的传输无关用例与请求/结果契约 | CLI 参数、HTTP 响应、具体驱动调用 |
| 外部适配层 | `fsq_agent/adapters/` | CLI、HTTP/SSE、静态服务及 Coding Agent SDK 的输入输出转换和组合 | 业务校验的唯一实现、平台执行语义 |
| 动态 Agent 策略 | `fsq_agent/agent/` | 预规划、提示上下文、验证策略和 SDK 无关运行协议 | OpenAI Agents SDK 对象构造、平台驱动实现 |
| 执行编排层 | `fsq_agent/execution/` | 动态/确定性执行、Case 生命周期、取消/清理、候选 Case 录制 | 传输格式、具体平台动作实现 |
| 平台无关执行核心 | `fsq_agent/core/` | Runner、证据处理、稳定执行接口和机制 | 具体 Playwright、uiautomator2、pywinauto、Appium 实现 |
| 平台驱动层 | `fsq_agent/drivers/<platform>/` | 平台动作、观察、后端错误规范化和可选依赖 | 完整用例编排、HTTP/CLI 逻辑 |
| 运行网关 | `fsq_agent/harnesses/` | 组合 CommonTools、单个平台 Driver、运行上下文、证据和评估器 | 外部传输或持久化协议所有权 |
| 环境管理 | `fsq_agent/environments/` | 主机支持判断、依赖/可执行文件发现、就绪与安装检查 | UI 自动化动作；LLM Provider 登录 |
| Case 语言 | `fsq_agent/case_dsl/` | `*.fsq.yaml` 加载、验证、别名、生命周期元数据和步骤适配 | Case 用例编排或实际执行 |
| 基础与支撑模块 | `config`、`models`、`capabilities`、`providers`、`observation`、`report`、`knowledge`、`skills`、`tools` | 各自 SPEC 定义的单一职责 | 为了“层次统一”而强行并入其他目录 |
| 前端源码 | `frontend/` | Vite 工作区及独立前端应用源码 | Python 传输实现或生成资产的源代码所有权 |

### 三组最容易混淆的分类

1. `application` 与 `adapters`：前者决定用例规则，后者只把 CLI、HTTP 或 SDK 输入转换为用例调用，再把结果转换出去。
2. `core`、`harnesses` 与 `drivers`：Core 决定平台无关的执行规则；Harness 组装运行期能力；Driver 执行某个平台的真实动作。
3. `providers` 与 `environments/providers`：前者是 LLM Provider；后者是主机/平台运行环境 Provider。名称相似，但所有权不同。

## 新文件的归类方法

新增或移动文件前，依次回答：

1. 它定义的是当前受支持行为，还是只适配某种输入输出？
2. 去掉 CLI、HTTP、SDK 或具体自动化后端后，它是否仍然成立？
3. 它协调的是完整用例、执行生命周期、单步机制，还是一个真实平台动作？
4. 哪个模块应是这条规则的唯一修改点？
5. 目标模块的 `SPEC.md` 是否已声明该职责、依赖和公共接口？
6. 移动后是否会出现反向依赖、循环依赖、跨模块私有导入或重复类型？

若第 5 或第 6 个问题无法明确回答，不应先移动文件，应先澄清架构契约。

## 未来是否还需要迁移

默认答案是：**不需要周期性迁移，也不以目录“更像某种架构模板”为目标。** 只有出现可验证的所有权或依赖问题时，才发起新的迁移。

### 应考虑迁移的信号

- 同一业务规则在两个以上入口重复实现并开始产生差异。
- 一个模块经常因不相关需求被修改，说明它承担了多个变化原因。
- 实际依赖违反根 `SPEC.md` 的依赖图，或出现循环依赖。
- 外部 SDK、传输对象或具体后端类型泄漏进平台无关模块。
- 其他模块必须导入某个模块的 `_private` 文件才能完成正常工作。
- 某个兼容转发层已经没有受支持调用者，却继续造成双入口或双所有者。
- 新平台或新入口只能通过复制现有编排才能接入。
- 当前目录与相关模块 `SPEC.md` 的所有权描述持续不一致。

### 不足以支持迁移的理由

- 目录文件较多，或名称主观上不够漂亮。
- 希望套用 Clean Architecture、DDD、Repository 或其他模式。
- 单个文件暂时较长，但仍只有一个清晰变化原因。
- 为可能永远不会出现的未来需求预建抽象。
- 仅为了减少相对导入、统一层级深度或追求完全对称。

## 长期目标与完成标准

长期目标是稳定的职责图，而不是稳定不变的文件树。一个健康状态应满足：

- 每条重要规则有且只有一个规范所有者。
- 外部入口依赖 Application 和公共执行契约，内层不反向依赖 Adapter。
- 平台无关机制不导入具体 SDK、传输或自动化后端类型。
- 新平台主要增加 Driver、Environment Provider 和 Harness 组合，而不复制核心流程。
- 公共 API 从模块入口显式导出；跨模块调用不依赖私有实现。
- 兼容层只转发同一对象，不复制逻辑或状态，并有明确保留依据。
- 根 `SPEC.md` 的模块表和依赖图与实际代码一致。
- 新同学可以根据“规则所有权”定位修改点，而无需依赖迁移历史。

当这些条件成立时，继续搬目录通常会增加风险而没有收益，应停止迁移。

## 迁移判断标准

建议用以下门槛决定是否启动一次目录迁移。所有必需项都应满足：

| 判断项 | 必需证据 |
| --- | --- |
| 问题真实存在 | 重复实现、错误依赖、私有跨界导入、循环依赖或职责冲突的具体路径 |
| 目标所有者明确 | 目标模块的当前职责、公共接口与允许依赖能够写成当前事实 |
| 收益大于成本 | 能减少规则副本、依赖方向或维护触点，而不仅是改名 |
| 行为边界明确 | 明确哪些 CLI、HTTP、Case、配置和运行行为必须保持不变 |
| 可分批验证 | 每一批均可独立测试、审计、回退，并保持可发布 |
| 兼容策略明确 | 哪些旧公共入口保留、转发或删除，以及依据是什么 |
| 收尾条件明确 | 不留下永久双实现、无依据转发层或过渡性私有导入 |

## 执行规范

目录迁移属于项目开发，必须显式通过 `/spec-driven <设计文档路径或直接变更请求>` 发起。执行时遵循以下顺序：

1. 盘点现有调用者、导入方向、公共入口、测试、打包资源和运行时发现机制。
2. 读取根与相关模块 `SPEC.md`，判断目标所有权或依赖是否需要 SPEC delta。
3. 若需要 SPEC delta，先更新 SPEC，并在修改非 SPEC 文件前取得确认。
4. 把迁移拆成职责完整的批次；每批保持用户可见行为不变，除非已确认的 SPEC 明确改变行为。
5. 先建立公共契约和回归测试，再移动实现与调用者。
6. 兼容入口只能薄转发到唯一实现，不复制逻辑、模型或可变状态。
7. 同一批次更新源码、测试、打包配置、文档引用和所有受影响的导入。
8. 运行聚焦测试、完整测试、Lint/格式检查，以及 SPEC 与实现的一致性审计。
9. 仅当旧实现无受支持调用者、无打包依赖且验证通过后，才删除过渡路径。
10. 记录迁移原因、边界、不变量和收尾结果；不要把历史叙事写进 `SPEC.md`。

## 代码评审检查清单

- [ ] PR 说明指出了具体的所有权或依赖问题。
- [ ] 目标路径与根/模块 `SPEC.md` 一致。
- [ ] 没有新增跨模块私有导入。
- [ ] 没有从内层模块反向导入 `adapters`。
- [ ] 没有复制 Request、Result、Event、Error 或领域模型。
- [ ] 兼容导出保持对象身份且不拥有行为。
- [ ] 用户可见契约的保持或变更有测试和 SPEC 依据。
- [ ] 打包、静态资源和入口点随目录变化同步更新。
- [ ] 过渡文件有删除条件，不会成为永久第二实现。
- [ ] 完整验证和 SPEC 实现审计已通过。
